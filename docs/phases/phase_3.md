# Phase 3 — Media Generation Layer

---

## What Phase 3 Is and Why It Is the Riskiest Phase

Phase 3 is the most technically unpredictable phase in the entire build. Every other phase deals with things that are largely within your control — data models, API endpoints, LLM prompts. Phase 3 deals with external rendering tools, audio generation libraries, file system operations, subprocess calls, and format compatibility — all of which can fail in ways that are unrelated to your code and that take time to diagnose.

The cardinal rule of Phase 3 is: prove each component works with the simplest possible hardcoded input before building anything around it. A HyperFrames render that produces one scene of solid color text is worth more right now than a sophisticated scene templating system that has never actually rendered. A TTS call that produces a 5-second audio clip is worth more than an audio pipeline designed to handle 10-minute scripts. You build from proven foundations outward, never from ambitious designs inward.

The second rule is: never stack unproven dependencies. Each component of the media pipeline — video rendering, TTS, transcription, captions — is proven independently before they are connected. If HyperFrames rendering and TTS are both untested and you connect them at the same time, a failure tells you nothing about which one is broken.

The third rule is: every generated file lands in a predictable location. Not wherever the tool decided to put it, not in a temp directory that gets cleaned up, not in a path that varies by operating system. You define the output directory structure in Phase 0 and every tool in Phase 3 is configured to write into that structure.

---

## Phase 3 — Step 1: Prove HyperFrames Works With a Hardcoded Scene

**What this step is about:**

Before writing any code that generates HyperFrames content from agent output, you verify that HyperFrames itself works on your machine with a completely hardcoded input. This is not about integration. This is about answering the single most important question of this phase: does the rendering tool work at all in your environment?

---

**What HyperFrames is and how it works:**

HyperFrames is a rendering engine that converts HTML, CSS, and JavaScript into video frames and assembles them into an MP4. It runs via a Node.js CLI. The workflow is: you write an HTML file that defines the visual content and timing of your video, you run `npx hyperframes render` pointing at that file, and it produces an MP4.

The HTML file is not a regular webpage. It uses HyperFrames-specific conventions to define scenes, timing, transitions, and captions. Each scene is an HTML element with HyperFrames timing attributes. The renderer processes these elements frame by frame, capturing the visual state at each frame interval, and assembles the frames into video.

---

**The hardcoded test you are running:**

You write the simplest possible HyperFrames HTML file by hand — not generated by any agent, not templated, just a static HTML file you write directly. This file contains:

One scene with a solid colored background. A single line of large bold white text in the center. A duration of 5 seconds. No audio, no transitions, no captions, no dynamic content.

You run `npx hyperframes render` on this file and verify that an MP4 file is produced. You open the MP4 and confirm it is a 5-second video showing the colored background and the text.

That is the entire test. If it works, you have de-risked the most important dependency in this phase. If it does not work, you are discovering the problem now — not after you have built a sophisticated templating system around it.

---

**What to do if this test fails:**

If the `npx hyperframes render` command is not found, Node.js is not installed or npx is not available. Install Node.js 18 or higher and verify that `node --version` and `npx --version` both return version numbers before proceeding.

If the command runs but produces an error about the HTML file format, consult the HyperFrames repository documentation. The HTML file structure has specific requirements. Check the `hyperframes/hyperframes` repository examples for the minimum valid file structure and match it exactly.

If the command runs, completes without errors, but the output file is blank, corrupted, or zero bytes, there is likely a dependency issue in the HyperFrames installation. Try running `npx hyperframes init` in a fresh directory to generate a scaffolded example project, and test rendering that scaffolded example before testing your own file.

If you cannot resolve the HyperFrames issue within a fixed time budget — no more than 30 to 45 minutes of troubleshooting — switch to the fallback plan. The fallback plan is documented at the end of this phase. Do not let HyperFrames troubleshooting consume the entire phase.

---

**What "done" looks like for Step 1:**

A real MP4 file exists on disk, produced by `npx hyperframes render` on your hardcoded HTML file, that you have opened and confirmed shows the expected content. You know which command to run, what the output path is, and roughly how long rendering takes for a 5-second clip. You have established the baseline.

## Phase 3 — Step 2: Understand the HyperFrames Scene Structure

**What this step is about:**

Before building the templating system that converts script agent output into HyperFrames HTML, you need to understand what HyperFrames HTML actually looks like for each of the scene types the script agent can produce. You learn this by studying the HyperFrames repository examples and by writing and rendering 2 to 3 more test scenes by hand — one for each scene type you plan to use.

The scene types from Phase 2 Step 5 that the script agent produces are: talking head, text overlay, title card, comparison split, list reveal, and b-roll description. You do not need to implement all six in the first pass. You implement the minimum set needed for the demo to work — typically title card, text overlay, and list reveal are enough for a short demo video.

---

**What you learn by doing this step:**

How HyperFrames represents scene timing — what attribute controls how long a scene displays, whether scenes are sequential automatically or need explicit ordering, and how transitions between scenes are defined.

How HyperFrames handles text — what CSS properties produce the large bold text appropriate for educational content videos, how text is positioned reliably across different content lengths, and whether there are font limitations.

How HyperFrames handles background colors — whether backgrounds are set via CSS background-color on the scene element, whether gradients work as expected, and whether there are any rendering quirks with specific colors.

How HyperFrames handles multiple scenes in sequence — whether they are defined as separate HTML elements in one file, as separate files, or as a different structure entirely.

What the output file naming convention is — does HyperFrames always name the output file the same thing, does it use the input filename, or is the output path configurable?

---

**The test scenes you build and render:**

Test scene 1 — Title card: A scene showing the video title in large centered text on a solid background. This represents how the script agent's title_card scene type renders.

Test scene 2 — Text overlay: A scene showing a background color with a large number or statistic displayed prominently, representing a list_reveal or key point moment.

Test scene 3 — Multi-scene sequence: A single HyperFrames file containing two scenes in sequence with a simple transition between them. This verifies that multi-scene rendering works before building the full templating system.

For each test, you render to MP4 and confirm the output looks correct. You note any rendering quirks — things that look different from what you expected based on the HTML — and you document them so the templating system accounts for them.

---

**What "done" looks like for Step 2:**

You have rendered 3 test scenes and confirmed the output for each. You understand how HyperFrames timing, text, backgrounds, and multi-scene sequences work in practice. You have enough knowledge to build the templating system without discovering fundamental HyperFrames limitations halfway through.

## Phase 3 — Step 3: Build the Scene Templating System

**What this step is about:**

Now you build the layer that takes a Script object from the script agent and converts it into a HyperFrames HTML file. This is the bridge between the AI layer and the rendering layer. It is purely mechanical — no LLM involved, no judgment calls. It takes structured data in and produces an HTML file out.

The core principle of this layer is that the template and the data are always separate. The template defines the structure and styling of each scene type. The data — the text, colors, duration — is filled into the template at render time. You can change how a title card looks without touching any agent code. You can update the brand colors without rerunning any agent. The template and the data are independent.

---

**The architecture of the templating system:**

The templating system has two parts.

The first part is a set of scene templates — one for each scene type the script agent can produce. Each template is a block of HyperFrames HTML that defines the layout and styling for that scene type, with placeholder slots where the data will be inserted. The placeholder slots are for things like the text content, the background color, and the duration.

The second part is the assembly function — the code that takes a complete Script object, iterates through its scenes, picks the right template for each scene's scene_type, fills in the data from the scene object, concatenates all the rendered scene blocks into one complete HyperFrames HTML document, and writes that document to disk.

---

**The scene templates you need to build:**

For each scene type, the template needs to define how it looks in a way that is consistent with the creator's visual style from the DNA profile. The creator's dominant colors become the background color pool. The creator's text style — bold, large, high contrast — is encoded in the CSS of the template.

Title card template: Full-screen solid background using the creator's primary dominant color. Large centered text showing the scene's on_screen_text. The voiceover_text is not displayed visually — it will be audio only. Duration set from the scene's duration_seconds.

Text overlay template: Solid background in the creator's secondary dominant color. Large bold text showing the on_screen_text with high contrast. Positioned according to the creator's established text position (top, center, or right-aligned based on the thumbnail_style.layout_pattern).

List reveal template: Solid background. A numbered or bulleted list where each item appears progressively. The list items come from the on_screen_text field, parsed as line-separated items.

Comparison split template: Background divided into two vertical halves, each a different color from the dominant palette. Left half label and right half label from the on_screen_text field, formatted as "LEFT|RIGHT" separator.

Talking head template: Since there is no actual video of the creator, this scene type renders as a text-focused scene with the on_screen_text displayed prominently and a visual indicator that this is a "presenter moment" — perhaps the creator's name or a simple graphic element.

B-roll description template: A descriptive text card showing what would be b-roll footage, rendered as a clean text scene with a softer background color to visually distinguish it from presenter scenes.

---

**The assembly function logic:**

The assembly function receives a Script object and a CreatorDNAProfile. The profile provides the color palette — specifically the dominant_colors list — which is used to assign colors to scene templates. The function does not call any LLM. It is pure data transformation.

The function iterates through the script's scenes in order. For each scene, it selects the template matching the scene's scene_type. It fills in the template's placeholder slots with the scene's voiceover_text (for audio), on_screen_text (for visual display), duration_seconds, and any color assignments from the creator's palette.

After processing all scenes — including the hook as the first scene and the outro as the last scene — the function wraps the assembled scene blocks in a HyperFrames document header and footer, producing a complete, valid HyperFrames HTML file.

The function writes this HTML file to a predictable location: `output/videos/` with a filename based on the asset ID. It returns the path to the HTML file so the render function knows where to find it.

---

**How to test the templating system:**

Take the Script object produced by the script agent during Phase 2 Step 8's manual chain run. Pass it through the assembly function. Open the resulting HTML file in a text editor and verify that it is valid HTML with correctly filled-in content — no unfilled placeholder slots, no missing closing tags, no escaped characters where there should be text.

Then pass the HTML file to HyperFrames and render it. Does the resulting video look like what the script describes? Does the text match the on_screen_text from the script scenes? Does the sequence match the scene order?

---

**What "done" looks like for Step 3:**

The assembly function takes a real Script object from Phase 2 and produces a HyperFrames HTML file. That HTML file renders to an MP4 without errors. The MP4 visually represents the script's scenes in order with the correct text content. The output file is in the `output/videos/` directory with a predictable filename.

## Phase 3 — Step 4: Integrate TTS to Produce the Voiceover Audio

**What this step is about:**

The video currently renders as a silent video — visual content only. In this step you add the voiceover audio by running the script's full_voiceover_text through a TTS system and producing an audio file. This step is done after the base video render works — not before, not simultaneously. Proven video render first, then audio.

---

**The TTS approach:**

The primary TTS tool is edge-tts, which runs locally with no API key and produces acceptable-quality voice output. The workflow is: pass the full_voiceover_text string to edge-tts with a selected voice and output it to a WAV or MP3 file.

The voice selection for edge-tts matters for the demo. edge-tts provides a range of English voices with different tones and genders. For a tech/productivity creator persona, a clear, moderately paced male or female voice works well. You select one voice and use it consistently — the creator's "voice" in the demo is this TTS voice.

---

**The first TTS test:**

Before integrating TTS with the video pipeline, you prove it works standalone. You take a 2-to-3-sentence sample of text from the script's hook and run it through edge-tts directly, producing an audio file. You play the audio file. You confirm it sounds like a recognizable voice reading the text correctly — no garbled words, no missing content, acceptable pacing.

If edge-tts is not available or produces poor quality for your use case, the fallback is to run the script text through the system's built-in text-to-speech (macOS has `say`, Windows has PowerShell speech synthesis) and output to a file. This produces lower quality but always works on the host machine. ElevenLabs is the upgrade path if quality matters more than zero-dependency operation.

---

**Integrating audio with the video:**

Once TTS produces an audio file, you need to combine it with the rendered video. There are two approaches:

Approach 1 — HyperFrames audio integration: HyperFrames supports audio tracks in its HTML format. You provide the audio file path in the HyperFrames document and the renderer embeds the audio in the output MP4. This is the cleaner approach because everything happens in one render step.

Approach 2 — ffmpeg post-processing: After HyperFrames renders the silent video and TTS produces the audio file, you use ffmpeg to combine them into a single MP4 with `ffmpeg -i video.mp4 -i audio.mp3 -c:v copy -c:a aac output_with_audio.mp4`. This approach requires ffmpeg to be installed but is more reliable because you are not relying on HyperFrames to handle audio correctly.

For the hackathon, use Approach 2 as the primary path. It is more explicit, the failure modes are more predictable, and ffmpeg is a well-understood tool. If ffmpeg is not installed, install it before proceeding — it is a standard tool available on all platforms.

---

**The audio timing consideration:**

The TTS audio duration will likely not match the video duration exactly. The script's estimated_duration_seconds is an estimate based on word count and assumed speaking pace — the actual TTS output may be longer or shorter.

You handle this in one of two ways: either you accept the mismatch and let the video and audio end at different times (acceptable for a demo), or you adjust the video length to match the audio length by modifying the scene durations proportionally before rendering.

For the hackathon, accept the mismatch unless it is severe (more than 20% difference). A video that ends a few seconds before the audio, or vice versa, is not a critical demo failure. A perfect timing match is polish that belongs in the stretch list, not the core build.

---

**How to test TTS integration:**

Run the full pipeline for the seed creator's script: assemble the HTML, render the video, generate the TTS audio, combine them with ffmpeg. Play the resulting MP4. Confirm that the audio plays, the video plays, they are reasonably synchronized, and the output is a single MP4 file with both video and audio tracks in the `output/videos/` directory.

---

**What "done" looks like for Step 4:**

The TTS call takes the full_voiceover_text from the script and produces an audio file. ffmpeg combines the audio file and the silent video into a single MP4 with both tracks. The combined MP4 plays correctly. The output file is in `output/videos/` with a predictable filename. The process runs without manual intervention.

## Phase 3 — Step 5: Generate Captions via Transcription

**What this step is about:**

Captions are added by running the audio track of the rendered video through faster-whisper, which produces a transcript with word-level timestamps. Those timestamps are used to create caption overlays that are synchronized with the audio. This step comes after the audio-included video exists — you need the audio to transcribe it.

---

**Why transcribe audio you already have the text for:**

You might wonder why you run transcription on audio that was generated from text you already have. The reason is timing. The TTS system produces audio with natural pauses, breathing patterns, and variable word durations that are difficult to predict from text alone. Running transcription on the actual audio gives you accurate timestamps for where each word is spoken, which produces well-synchronized captions. If you use the script text directly for captions without timing information, captions will appear at the wrong moments.

---

**The transcription process:**

You run faster-whisper on the audio track of the combined MP4 (or on the TTS audio file directly, which is faster). You specify the "base" model for speed — "small" is acceptable if "base" produces accuracy issues, but "large" is unnecessary. faster-whisper returns a list of segments, where each segment contains the text spoken and the start and end timestamps in seconds.

You convert these segments into a caption format that HyperFrames or ffmpeg can embed in the video.

---

**Caption embedding approach:**

There are two approaches for embedding captions:

Approach 1 — SRT file with ffmpeg: Convert the faster-whisper segments into an SRT subtitle file. Use ffmpeg to burn the captions into the video: `ffmpeg -i video_with_audio.mp4 -vf subtitles=captions.srt output_captioned.mp4`. Burned-in captions are always visible regardless of player settings. This is the right choice for a demo where you cannot control the viewer's player.

Approach 2 — HyperFrames caption blocks: If HyperFrames supports caption overlays natively, you can pass the transcript segments back into the HyperFrames HTML and re-render. This produces cleaner results but requires a second render pass.

For the hackathon, use Approach 1. SRT files are simple to generate from faster-whisper output, ffmpeg handles the embedding reliably, and you do not need a second render pass.

---

**The SRT format:**

An SRT file is a plain text file where each caption entry has a sequential number, a timestamp range in the format `HH:MM:SS,mmm --> HH:MM:SS,mmm`, and the caption text on the next line, followed by a blank line. Converting faster-whisper's segment output into this format is straightforward string formatting — no external library needed.

---

**Caption styling consideration:**

By default, ffmpeg's subtitle burning uses small white text at the bottom of the frame. For a tech/productivity video demo, larger, higher-contrast captions look better. ffmpeg allows you to specify subtitle style options including font size, font color, outline color, and position. The creator's text style from the DNA profile — white text with black outline — should inform the caption style.

---

**How to test captions:**

Run faster-whisper on the TTS audio file. Examine the segments — do the timestamps make sense? Does the text match the original script? Convert to SRT. Burn into the video with ffmpeg. Play the resulting MP4 and verify that captions appear in sync with the audio.

Edge case to test: What happens if faster-whisper returns very short segments — one word per segment? The SRT will have many entries and captions will flash rapidly. If this happens, merge segments that are shorter than 2 seconds into combined entries before generating the SRT.

---

**What "done" looks like for Step 5:**

faster-whisper produces accurate timestamps for the TTS audio. An SRT file is generated correctly from the segments. ffmpeg burns the captions into the video. The final MP4 shows captions that are reasonably synchronized with the audio. The process runs without manual intervention and the output is in `output/videos/` with a predictable filename.

## Phase 3 — Step 6: Build the Thumbnail Rendering Pipeline

**What this step is about:**

The thumbnail agent from Phase 2 produces SVG markup. In this step you build the pipeline that converts that SVG markup into a PNG file. This is the simplest media generation task in Phase 3 because it is a single function call — SVG in, PNG out — with no subprocess, no audio, no timing.

---

**Proving cairosvg works first:**

Before integrating with the thumbnail agent output, you prove cairosvg works with a hardcoded SVG string. You take a simple SVG — a colored rectangle with text — and call cairosvg to convert it to a PNG. You open the PNG and confirm it rendered correctly.

If cairosvg is not installable on your system (it sometimes has issues on Windows due to Cairo library dependencies), the fallback is resvg-py, which is a pure-Python SVG renderer with no system library dependencies. Install resvg-py and test it with the same hardcoded SVG before concluding cairosvg is not an option.

---

**The rendering pipeline:**

The thumbnail rendering function takes the SVG source string from a ThumbnailVariant object, a target output path, and the asset ID. It calls cairosvg (or resvg-py) to convert the SVG to a PNG at the target path. It returns the path to the PNG file.

The output path follows the directory structure from Phase 0: `output/thumbnails/` with a filename that includes the asset ID and variant number, for example `thumb_assetid_v1.png`.

After rendering, the function updates the ThumbnailVariant's png_path field with the output path. The variant is now ready for the scorer agent to evaluate.

---

**Handling SVG rendering failures:**

LLM-generated SVG can contain issues that cause rendering failures — invalid color values, malformed paths, missing attributes. The rendering function should handle these failures without crashing the entire pipeline.

When cairosvg raises an exception, the function logs the error and the first 500 characters of the SVG source (for debugging), marks that variant's render status as failed, and continues to the next variant. If all variants fail to render, it returns an error that the orchestrator can surface clearly rather than produce a silent failure.

---

**Testing the thumbnail pipeline with real agent output:**

Take the SVG source strings produced by the thumbnail agent during Phase 2 Step 8's manual chain run. Pass each one through the rendering function. Examine the resulting PNGs:

Do they render without errors? If one fails, look at the SVG source — is there an invalid element or attribute? Fix the thumbnail agent's system prompt to avoid generating that construct.

Do they look like YouTube thumbnails — 1280 pixels wide, 720 pixels tall, readable text, correct colors?

Do they visually reflect the creator's thumbnail style from the DNA profile — solid color background, bold white text, creator placeholder in the correct position?

---

**What "done" looks like for Step 6:**

cairosvg or resvg-py converts the thumbnail agent's SVG output to PNG without errors. The PNG files are 1280x720, visually correct, and stored in `output/thumbnails/` with predictable filenames. Rendering failures are handled gracefully with clear error messages rather than exceptions.

## Phase 3 — Step 7: Build the Full Media Pipeline Function

**What this step is about:**

Now that every component works independently — HyperFrames renders video, TTS generates audio, ffmpeg combines them, faster-whisper generates captions, ffmpeg burns them in, and cairosvg renders thumbnails — you build the single function that orchestrates all of these steps in sequence for one complete asset.

This function is what the Phase 4 orchestrator will call. It takes a GeneratedAsset object (containing the script and thumbnail variants), runs every media generation step, and returns an updated GeneratedAsset with all file paths filled in and all render statuses updated.

---

**The sequence this function executes:**

Step 1 — Generate TTS audio: Call edge-tts with the script's full_voiceover_text. Save to `output/videos/[asset_id]_audio.mp3`. Record the path.

Step 2 — Assemble HyperFrames HTML: Call the scene templating system from Step 3. Pass the script object and creator profile. Save the HTML to `output/videos/[asset_id].html`. Record the path.

Step 3 — Render silent video: Call HyperFrames CLI via subprocess, pointing at the HTML file. Wait for the process to complete. Verify the output MP4 exists. Save to `output/videos/[asset_id]_silent.mp4`.

Step 4 — Combine audio and video: Call ffmpeg to merge the silent MP4 and the audio MP3. Save to `output/videos/[asset_id]_with_audio.mp4`.

Step 5 — Transcribe audio for captions: Call faster-whisper on the audio file. Generate the SRT file. Save to `output/captions/[asset_id].srt`.

Step 6 — Burn captions into video: Call ffmpeg with the subtitle filter. Save to `output/videos/[asset_id]_final.mp4`. This is the deliverable video.

Step 7 — Render all thumbnail variants: For each ThumbnailVariant in the asset, call the thumbnail rendering function. Update each variant's png_path.

Step 8 — Update the asset object: Set the video.file_path to the final MP4 path. Set video.has_captions to true. Set video.render_status to complete. Set video.duration_seconds to the actual rendered duration. Return the updated asset.

---

**Error handling within the pipeline function:**

Each step is wrapped in error handling. If any step fails, the function sets the video.render_status to failed, records which step failed, and returns the asset in its partial state rather than raising an exception that kills the entire pipeline. The orchestrator in Phase 4 will surface this failure cleanly.

The critical failure mode to handle explicitly is HyperFrames rendering failure — if the subprocess call to HyperFrames returns a non-zero exit code, the function captures the stderr output, logs it, and surfaces a readable error: "HyperFrames render failed: [stderr content]."

---

**Timing the full media pipeline:**

After building the full pipeline function, run it once on the seed creator's script and time the complete execution. Record how long each step takes individually and the total time. This information determines the demo strategy:

If the total time is under 60 seconds, live rendering during the demo is viable.

If the total time is 60 to 180 seconds, live rendering is possible but you should narrate the wait — "the render is happening now, which typically takes about 2 minutes for a video this length."

If the total time is over 180 seconds, pre-render the demo video and load it from disk during the demo. Be transparent about this — tell the judges the render happened before the demo to avoid the long wait, and offer to show a real render if they want to wait for it.

---

**What "done" looks like for Step 7:**

One call to the full media pipeline function, with a real Script object and real ThumbnailVariant objects from Phase 2, produces all of the following in `output/`:

A final MP4 video with audio and burned-in captions in `output/videos/`.
An SRT captions file in `output/captions/`.
PNG thumbnail files for each variant in `output/thumbnails/`.
The GeneratedAsset object is returned with all file paths filled in, render status set to complete, and no null values where real paths should be.

## Phase 3 — Step 8: Verify Predictable Output Paths and File Serving Readiness

**What this step is about:**

Every file the media pipeline produces must be in a location and with a filename that the API can serve to the frontend predictably. This is the final verification step before Phase 4 wires the pipeline into the API.

---

**The output directory structure and naming convention:**

All generated files follow this convention:

Videos: `output/videos/[asset_id]_final.mp4`
Audio files (intermediate): `output/videos/[asset_id]_audio.mp3`
Silent video (intermediate): `output/videos/[asset_id]_silent.mp4`
Audio-combined video (intermediate): `output/videos/[asset_id]_with_audio.mp4`
Captions SRT: `output/captions/[asset_id].srt`
Thumbnail PNGs: `output/thumbnails/[asset_id]_v[1,2,3].png`

Intermediate files (audio, silent video, audio-combined video before captions) can be deleted after the final MP4 is produced. The deliverables are the final MP4, the SRT, and the thumbnail PNGs.

---

**Verifying the API can serve these files:**

The Phase 1 stub endpoints for `/output/video/{filename}` and `/output/thumbnail/{filename}` currently return placeholder responses. In this step you verify that those endpoints, when updated with real file-serving logic, can successfully serve the files produced by the media pipeline.

You make a GET request to `/output/video/[asset_id]_final.mp4` and confirm the response is an MP4 file that plays in a browser. You make a GET request to `/output/thumbnail/[asset_id]_v1.png` and confirm the response is a PNG that displays correctly.

The frontend VideoPreview component needs a URL it can pass to an HTML5 video element's src attribute. The frontend ThumbnailPicker component needs a URL it can pass to an img element's src attribute. These two endpoints provide those URLs.

---

**What "done" looks like for Step 8:**

Every file produced by the media pipeline is in a predictable location with a predictable filename. The API serves those files correctly. The frontend can load a video by making a request to the video endpoint and load a thumbnail by making a request to the thumbnail endpoint. No file is in a temp directory or a path that might change between runs.

## Phase 3 — The Fallback Plan

**When to execute the fallback:**

If HyperFrames rendering cannot be made to work within a fixed time budget, or if it works but is too slow for a live demo, execute the fallback plan. The fallback does not compromise the core value of the project — the decision layer is the innovation, not the render.

---

**The fallback video approach:**

Pre-render one video using HyperFrames before the demo. This pre-rendered video is stored as a static asset. During the demo, when the pipeline "renders" the video, it copies the pre-rendered video to the output path for the current asset. From the frontend's perspective, a video file appears in the expected location. From the judge's perspective, the video plays as expected.

Be transparent about this in the demo: "The video rendering happens in the background — for the demo I have a pre-rendered version ready so we do not have to wait two minutes for rendering. The render itself is real — we can show it live if you want to see it."

---

**The fallback thumbnail approach:**

If cairosvg cannot be installed or the LLM-generated SVG consistently fails to render, pre-generate 2 to 3 static PNG thumbnails that represent the creator's style. During the demo, the thumbnail agent's SVG output is shown in the decision log (proving the agent ran), but the displayed thumbnails are the pre-generated static ones.

---

**The absolute minimum media output:**

If every rendering approach fails, the minimum viable media output is: the script displayed as formatted text, the thumbnail shown as a pre-designed static image, and the metadata displayed in the UI. The scorer still runs, the decision log still shows the reject/regenerate cycle, and the core value proposition is still demonstrable. The judges are evaluating the intelligence of the system, not the quality of the video render.

---

## Phase 3 — The Done Definition

Phase 3 is complete when all of the following are true simultaneously.

HyperFrames renders a multi-scene video from agent-generated script output and produces a real MP4 file. If HyperFrames is being used in fallback mode, the fallback video is pre-rendered and ready.

TTS generates voiceover audio from the script's full_voiceover_text and produces a playable audio file.

ffmpeg combines the video and audio into a single MP4 with both tracks playing correctly.

faster-whisper transcribes the TTS audio and produces an SRT captions file with timestamps.

ffmpeg burns the captions into the video and produces a final MP4 with visible, reasonably synchronized captions.

cairosvg or resvg-py renders the thumbnail agent's SVG output into PNG files at the correct dimensions.
